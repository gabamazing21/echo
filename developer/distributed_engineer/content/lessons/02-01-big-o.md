# Big-O: reasoning about time & space

> **Step 2 · Data structures & algorithms · Week 1**
> Concept: *time vs space complexity, the common classes, amortized & best/avg/worst case*

You can already write Go that *works*. This lesson teaches you to reason about
what your code will *cost* — how its running time and memory grow as the input
grows. That shift, from "is it correct?" to "how does it scale?", is the entire
mindset of **Big-O notation**. Don't skim it; everything in Step 2 sits on top of
it.

## Why this matters

A distributed system is just code that runs on a lot of data across a lot of
machines. An algorithm that's fine on your laptop with 1,000 records can melt a
production cluster at 1 billion. The difference between an O(n) and an O(n²) pass
over a request batch isn't academic — it's the difference between a 50ms response
and a timeout, between one node and a fleet, between a cheap bill and a fire. When
you design replication, sharding, or a gossip protocol later, you'll constantly
ask: *how does the work grow with the number of nodes, keys, or messages?* Big-O
is the language you'll answer that question in. It also lets you compare two
solutions **before** writing either — reasoning about cost, not just correctness.

## 1. What Big-O actually measures

Big-O describes how a quantity (time or memory) grows as the input size `n` grows,
**ignoring constant factors and lower-order terms**. We care about the *shape* of
the curve, not the exact count of operations. `3n + 50` and `n` are both **O(n)**:
double the input, roughly double the work. Constants get dropped because for large
`n` they stop mattering — `O(n)` beats `O(n²)` eventually no matter how big the
constants are.

```go
package main

import "fmt"

// sumFirst does a fixed amount of work regardless of how big s is: O(1).
func sumFirst(s []int) int {
	if len(s) == 0 {
		return 0
	}
	return s[0] // one access, no loop — constant time
}

func main() {
	fmt.Println(sumFirst([]int{10, 20, 30})) // 10
}
```

The rule of thumb: **count how the number of basic steps depends on `n`**, then
strip the constants. One step or a thousand fixed steps are both O(1).

## 2. O(1): constant time

Work that doesn't grow with the input is **constant time**. A map lookup, an array
index, pushing onto a stack — all O(1). This is the gold standard.

```go
package main

import "fmt"

func main() {
	owners := map[string]int{"key-a": 1, "key-b": 2, "key-c": 3}
	// Looking up which node owns a key is O(1) — independent of map size.
	node := owners["key-b"]
	fmt.Println(node) // 2
}
```

In a distributed system, an O(1) "which node owns this key?" lookup (via a hash
ring or a map) is what lets routing stay fast no matter how many keys exist.

## 3. O(n): linear time

One pass over the input is **linear**. Touch each of `n` elements a constant
number of times and you're O(n).

```go
package main

import "fmt"

// max scans every element once: O(n) time, O(1) extra space.
func max(s []int) int {
	best := s[0]
	for _, v := range s { // n iterations
		if v > best {
			best = v
		}
	}
	return best
}

func main() {
	fmt.Println(max([]int{3, 9, 2, 7})) // 9
}
```

Two separate loops over the same slice are `n + n = 2n`, still **O(n)** — we drop
the constant. Linear is usually the best you can do when you genuinely must look
at every item.

## 4. O(n²): nested loops

A loop inside a loop, each running ~`n` times, gives **quadratic** time: `n × n`.
This is where things start to hurt at scale.

```go
package main

import "fmt"

// hasDuplicate compares every pair: O(n^2). Fine for tiny n, deadly for large n.
func hasDuplicate(s []int) bool {
	for i := 0; i < len(s); i++ {
		for j := i + 1; j < len(s); j++ { // inner loop: ~n each time
			if s[i] == s[j] {
				return true
			}
		}
	}
	return false
}

func main() {
	fmt.Println(hasDuplicate([]int{1, 2, 3, 2})) // true
}
```

At n = 1,000 that's ~500,000 comparisons; at n = 1,000,000 it's ~5×10¹¹ — minutes
to hours. The same job is O(n) with a map (section 8). **Spotting an accidental
O(n²) is one of the highest-value skills you'll build here.**

## 5. O(log n): halving the problem

When each step throws away a *constant fraction* of the remaining input, the count
of steps is **logarithmic**. Binary search over a sorted slice is the classic:
each comparison halves the search space, so `n` shrinks to 1 in about `log₂ n`
steps (~20 steps for a million items).

```go
package main

import "fmt"

// binarySearch on a SORTED slice: O(log n) time.
func binarySearch(s []int, target int) int {
	lo, hi := 0, len(s)-1
	for lo <= hi {
		mid := (lo + hi) / 2 // discard half the range each pass
		switch {
		case s[mid] == target:
			return mid
		case s[mid] < target:
			lo = mid + 1
		default:
			hi = mid - 1
		}
	}
	return -1
}

func main() {
	fmt.Println(binarySearch([]int{1, 3, 5, 7, 9, 11}, 7)) // 3
}
```

Logarithmic growth is wonderfully flat: going from a thousand to a billion items
only multiplies the work by ~3×. Balanced trees and many index lookups live here.

## 6. O(n log n): the sorting tier

Doing `log n` work for each of `n` elements — or merging halves recursively —
gives **O(n log n)**. This is the cost of good general-purpose sorting, and it's
the practical ceiling for "fast" algorithms over `n` items.

```go
package main

import (
	"fmt"
	"sort"
)

func main() {
	s := []int{5, 2, 9, 1, 7}
	sort.Ints(s) // Go's standard sort: O(n log n)
	fmt.Println(s) // [1 2 5 7 9]
}
```

A useful pattern: if an O(n²) brute force is too slow, **sorting first** (n log n)
often unlocks a faster overall solution — e.g. sort, then a single linear pass.

## 7. O(2ⁿ): exponential — the cliff

When work *doubles* with each added element, you're **exponential**, and you fall
off a cliff almost immediately. Naive recursive Fibonacci re-computes the same
subproblems over and over:

```go
package main

import "fmt"

// fib is O(2^n): each call spawns two more. n=40 is already ~a billion calls.
func fib(n int) int {
	if n < 2 {
		return n
	}
	return fib(n-1) + fib(n-2)
}

func main() {
	fmt.Println(fib(10)) // 55 — fast; try fib(45) and watch it crawl
}
```

Exponential algorithms are unusable beyond tiny inputs. The fix here is *memoizing*
or going bottom-up (an O(n) loop) — the kind of trade you'll make constantly.

## 8. Time vs space: the trade-off

Big-O applies to **memory** too. `hasDuplicate` from section 4 was O(n²) time and
O(1) space. Trade memory for speed by remembering what you've seen in a map:

```go
package main

import "fmt"

// hasDuplicateFast: O(n) time, O(n) space — the classic time/space trade-off.
func hasDuplicateFast(s []int) bool {
	seen := make(map[int]struct{}, len(s)) // O(n) extra memory
	for _, v := range s {                  // O(n) time
		if _, ok := seen[v]; ok {
			return true
		}
		seen[v] = struct{}{}
	}
	return false
}

func main() {
	fmt.Println(hasDuplicateFast([]int{1, 2, 3, 2})) // true
}
```

Note `map[int]struct{}` — a set with zero-byte values. We spent O(n) memory to cut
time from O(n²) to O(n). At scale that trade is almost always worth it, but the
memory cost is real: in a distributed system, "remember everything seen" can blow
a node's RAM. Always state **both** the time *and* space complexity.

## 9. Best, average & worst case

A single algorithm can have different costs depending on the input. Linear search
finds the target on the first element in the **best case** (O(1)) but scans all `n`
in the **worst case** (O(n)); on random data the **average** is ~n/2, still O(n).

```go
package main

import "fmt"

// indexOf: best case O(1) (target first), worst case O(n) (target last/absent).
func indexOf(s []int, target int) int {
	for i, v := range s {
		if v == target {
			return i // could happen on iteration 1 ... or n
		}
	}
	return -1
}

func main() {
	fmt.Println(indexOf([]int{4, 8, 15, 16}, 15)) // 2
}
```

Big-O usually refers to the **worst case** unless stated otherwise, because that's
what bounds your guarantees. But average case drives real-world performance, and
the gap between them matters (quicksort is O(n log n) average, O(n²) worst).

## 10. Amortized analysis: why `append` is O(1)

Sometimes a single operation is occasionally expensive but *cheap on average over
a sequence* of operations. That average is the **amortized** cost. Go's slice
`append` is the canonical example: usually it writes into spare capacity (O(1)),
but when capacity runs out it allocates a bigger backing array and copies
everything (O(n)). Because capacity **doubles** each time it grows, those costly
copies are rare enough that the *average* cost per append is **amortized O(1)**.

```go
package main

import "fmt"

func main() {
	s := make([]int, 0) // grows on demand
	for i := 0; i < 8; i++ {
		s = append(s, i)
		fmt.Println("len", len(s), "cap", cap(s)) // cap jumps: 1,2,4,8 — doubling
	}
	// Total copying across n appends is ~2n, so per-append cost averages to O(1).
}
```

The intuition: building a slice of `n` items with `append` costs O(n) total, not
O(n²), even though some individual appends triggered a full copy. This is exactly
why you can `append` in a loop without fear — and why pre-sizing with
`make([]T, 0, n)` is a nice optimization, not a correctness requirement.

## 11. Cheat sheet

| Class | Name | Example | n=1,000 feels like |
|---|---|---|---|
| O(1) | constant | map/array access | instant |
| O(log n) | logarithmic | binary search | instant (~10 steps) |
| O(n) | linear | single scan | fast |
| O(n log n) | linearithmic | good sorting | fast |
| O(n²) | quadratic | nested loops / all pairs | sluggish |
| O(2ⁿ) | exponential | naive recursion | hopeless |

From top to bottom is best to worst. When you write a function, get in the habit
of stating its time *and* space class out loud — that one sentence is the whole
skill.

## Common interview gotchas

- **Θ vs O vs Ω.** O is only an *upper* bound — `n` is technically O(n²). Θ is a *tight* bound; Ω is a lower bound. Don't conflate "O" with "worst case": you can give an O-bound for best, average, *or* worst. State the **case and the bound separately** (quicksort is Θ(n log n) average, Θ(n²) worst).
- **Amortized ≠ average-case.** Amortized is a *guarantee over a sequence* of operations (any n appends cost O(n) total) with no randomness assumed; average-case is over a distribution of inputs. `append` is amortized O(1) because capacity doubling makes the O(n) copies exponentially rare.
- **Nesting multiplies, sequencing adds.** Two loops *after* each other are O(n); one *inside* the other is O(n²). A triangular inner loop (`j := i`) is still O(n²) — halving the work doesn't change the class.
- **Always quote both axes.** Every complexity answer needs *time and space*. The map-based dedup trades O(n) memory to cut time from O(n²) to O(n) — and at scale that memory cost is real, not free.
- **Multiplicative vs additive steps.** `i *= 2` is O(log n); `i++` is O(n). Spotting that one character is the difference between logarithmic and linear.
