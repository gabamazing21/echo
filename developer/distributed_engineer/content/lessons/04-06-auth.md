# Authentication — hashing, JWT & sessions

> **Step 4 · Build real backend APIs · Week 3**
> Concept: *authentication vs authorization*

Two different questions, often confused:

- **Authentication** — *who are you?* (login, proving identity)
- **Authorization** — *what are you allowed to do?* (permissions, ownership)

Get the words straight and the design gets clear. This lesson covers both, plus
the one thing you must never get wrong: password storage.

## Why this matters

Auth is where security bugs are most catastrophic and most common. Every service
needs it; doing it wrong leaks user data. This is also exactly the work you do on
Lokatalent — secure signup, login, and protected routes.

## 1. Never store passwords. Store a salted hash.

A password must be **impossible to recover** from your database, even if it leaks.
You don't encrypt it (reversible) — you **hash** it with a slow, salted algorithm
designed for passwords: **bcrypt** or **argon2**.

```go
import "golang.org/x/crypto/bcrypt"

// On signup: hash the password, store the hash.
hash, err := bcrypt.GenerateFromPassword([]byte(plain), bcrypt.DefaultCost)
// store `hash` (a []byte/string) in the users table — NEVER the plain password

// On login: compare the candidate against the stored hash.
err = bcrypt.CompareHashAndPassword(stored, []byte(candidate))
if err != nil {
	// wrong password -> 401
}
```

- **Salt** (a random per-password value) is baked into the bcrypt output, so two
  users with the same password get different hashes. bcrypt handles it for you.
- **Slow on purpose**: bcrypt's cost factor makes brute-forcing expensive.
- ❌ Never: plaintext, MD5/SHA-256 alone (too fast), reversible encryption, base64.

## 2. Proving identity after login: sessions vs JWTs

After a correct login, the server issues a credential the client sends on every
later request. Two common approaches:

| | Session (server-side) | JWT (stateless token) |
|---|---|---|
| What the client holds | an opaque session id (cookie) | a signed token containing claims |
| Where state lives | server (DB/Redis) | nowhere — it's in the token |
| Revoke instantly? | ✅ delete the session | ❌ hard (until it expires) |
| Scales across instances | needs shared session store | ✅ any instance can verify |
| Good for | classic web apps | APIs, microservices |

Neither is "better" — it's a trade-off between easy revocation and statelessness.

## 3. JWTs in practice

A JWT is three base64 parts (`header.payload.signature`). The payload holds
**claims** (e.g. `sub` = user id, `exp` = expiry). The signature proves the server
issued it — **a JWT is signed, not encrypted, so never put secrets in it.**

```go
import "github.com/golang-jwt/jwt/v5"

// Issue on successful login:
tok := jwt.NewWithClaims(jwt.SigningMethodHS256, jwt.MapClaims{
	"sub": userID,
	"exp": time.Now().Add(24 * time.Hour).Unix(),
})
signed, err := tok.SignedString([]byte(secret))   // give `signed` to the client

// Verify on each request:
parsed, err := jwt.Parse(signed, func(t *jwt.Token) (any, error) {
	return []byte(secret), nil
})
// err != nil OR !parsed.Valid -> 401
```

Always set `exp`. Keep the signing `secret` out of source (env var). Use HTTPS so
the token can't be sniffed.

## 4. Guarding routes with middleware

Authentication is just middleware (Step 4, lesson 2). It reads the token, verifies
it, and stashes the user id on the context for handlers to use:

```go
func RequireAuth(secret string) echo.MiddlewareFunc {
	return func(next echo.HandlerFunc) echo.HandlerFunc {
		return func(c echo.Context) error {
			raw := bearer(c.Request().Header.Get("Authorization")) // strip "Bearer "
			claims, err := verify(raw, secret)
			if err != nil {
				return echo.NewHTTPError(http.StatusUnauthorized, "invalid token")
			}
			c.Set("userID", claims["sub"])  // handlers read this
			return next(c)
		}
	}
}

protected := e.Group("/api", RequireAuth(secret))
```

## 5. Authorization: ownership checks

Authentication put a `userID` on the context. **Authorization** is using it:
a user may only touch *their own* bookmarks. That's a `WHERE user_id = $1` in your
query (or a 403 if they ask for someone else's id). Authentication without
authorization is a door with no walls.

## Common interview gotchas

- **"SHA-256 with a salt is fine for passwords."** Fast hashes are the *problem* — a GPU does billions/sec. Use a deliberately **slow** KDF (bcrypt/argon2/scrypt) with a tunable cost; the salt only stops rainbow tables, it doesn't slow brute force.
- **"JWTs are encrypted, so claims are private."** A JWT is **signed, not encrypted** — anyone can base64-decode the payload. Never put secrets in it; the signature only proves integrity/issuer.
- **"Just log the user out by deleting the token client-side."** A stateless JWT stays valid until `exp` no matter what — you can't revoke it. Mitigate with short TTL + refresh tokens, or a server-side denylist (which trades away statelessness).
- **"Tell the user whether it was a bad email or bad password."** Different messages (or different response *timings*) let attackers enumerate accounts. Return one identical "invalid credentials" 401 — and compare against a dummy hash even for unknown users to keep timing flat.
- **"`alg: none` / accepting the token's own alg is fine."** Classic JWT attack: attacker sets `alg:none` or swaps RS256→HS256 to forge tokens. Pin the expected algorithm server-side; never trust the header's `alg`.
